# Internal review — October 2026

This is an **internal** review (not a third-party audit). It covered every file of the repository, the live X1 program, the X1 / XEN / XEN Prime ecosystem and the community discussions of Aug–Oct 2026. It replaces the former `AUDIT_REPORT.md`, whose "production-ready / audited" claims were wrong.

## Verified on-chain state before v2 (2026-10-06)

- Program `57UE1U1t23ztg2noLp8pcpGW1B1Xw25rLH6ra9Mchea9` deployed 2026-04-07, 10 transactions total (deploy + init), **zero claims, zero bets**. All vaults held only rent.
- Upgrade authority: the architect wallet (the docs claimed "no admin keys / immutable").
- The deployed binary matched the local build byte-for-byte.

## Critical findings in v1 (all fixed in v2)

| # | Area | Finding | v2 fix |
|---|---|---|---|
| C1 | Program | Merkle leaf had no epoch and the receipt used a caller-chosen epoch → one leaf could be claimed again every epoch until the vault was empty | Leaf = domain ‖ epoch ‖ player ‖ tier ‖ score; one root per epoch PDA; receipt per (epoch, player, tier) |
| C2 | Program | Game RNG = slot byte ⊕ hash(player), resolved in the same instruction → predictable and revertible via CPI | Commit to the next slot, permissionless settlement, expiry = loss, top-level only |
| C3 | Program | Bankroll lost 52% of every losing stake (−24% EV for the house); High-Low had modulo bias (+13.7% EV for players); Jackpot had an 80% edge | Uniform 2% edge, exact odds (unit-tested), liability reservation, 0.25% exposure cap |
| C4 | Program/oracle | Oracle key had instant, unlimited control over the vault | Budget computed on-chain: ≤10% of the free pool, ≥6 days apart, data hash committed |
| C5 | Oracle | Base58 addresses lowercased → every claim impossible; a 1-wei burn to a bad address blocked every epoch; publisher did not match the program ABI | Raw 32-byte keys end-to-end; dust ignored; Anchor client from the generated IDL |
| C6 | Portal | Burn was a transfer to 0xdEaD (not XEN `burn()`); X1 address checked by length only | XEN `burn()` via IBurnRedeemable + ERC-165; bytes32 key |
| C7 | Frontend | Claim flow mocked; all 8 games used `Math.random()` and some showed fake wins | Rewired to the program; no mocks |
| C8 | Docs | "Immutable", "audited", "pool cannot go bankrupt", "NFT boosts live", fee tables — false | Rewritten |

## High / medium findings (selection)

- One vesting PDA per player blocked new claims for 180 days → missions per (epoch, player, tier).
- Tiers were exploitable: pick 3× and eject immediately for 1.5× (penalty 50%) → penalties 60%/75% on the unvested part (immediate eject < 1×).
- √XEN scoring rewarded splitting a burn across wallets (100 wallets ⇒ 10× score) → linear scoring by liquidity-adjusted market value.
- Root overwrite lost unclaimed allocations → per-epoch roots, 90-day window, then released to the pool.
- `release_dev_escrow` drained the vault below rent → escrow removed entirely.
- Referrer and NFT boost were user-supplied claim arguments → removed / computed by the oracle from on-chain holders.
- Oracle: cursor saved before publishing, failed chunks skipped, no finality, no dedup → stateless epoch files, finality depth per chain, abort instead of skip, dedup by (chain, tx, log).
- Solidity "X1" contracts (MoonForgeBase, MoonArtifacts, games…) could never run on X1 (SVM) → removed (history in git).
- `@faircrypto/xen-crypto` npm artifact lists wrong Optimism/Base XEN addresses → addresses verified on-chain and hard-coded.

## Second adversarial pass on v2 (2026-10-07)

A second internal adversarial pass (not independent) attacked the v2 program (every instruction, every lamport movement) before the mainnet upgrade. Every finding below is fixed in the code and covered by a test; where the third pass changed a fix, it is noted.

| # | Severity | Finding | Fix | Test |
|---|---|---|---|---|
| A1 | Critical | Forge Drops had no ceiling: a leaf with `score > total_score` (a lying or buggy oracle) could turn the drop into the whole free pool | `score ≤ total_score` for every leaf; total drops per epoch ≤ `reserve + max(reserve, 15 XNT)` | `expired randomness…` (InvalidProof), drop unit tests |
| A2 | Critical | Be-the-House shares were priced at the conservative value: many open bets depressed it, so an attacker could deposit cheaply and take value from existing LPs once the bets settled | Deposits priced at the optimistic value (pending bets counted as lost), withdrawals at the conservative one; aggregate cap: pending payouts ≤ 20% of the bankroll; `min_shares` / `min_lamports` slippage limits | `Be the House: shares are never cheaper…`, stress test audit |
| A3 | High | Anyone could pre-fund a PDA address (next Artifact, collection, a new vault) and make its creation fail forever | The program signs for its own PDA and hands the pre-funding to the payer before creating it | `Forge Drops…` (pre-funded asset address) |
| A4 | Medium | An expired Jackpot / lottery draw picked a new target block: a losing player could wait for a better block | Expired Jackpot → full refund (entry by entry, permissionless); expired lottery → no winner, never re-drawn (the prize then carried over; since the third pass, H2, it goes to the reward pool) | `expired randomness never re-rolls…` |
| A5 | Medium | First-LP share inflation on an empty bankroll | Permanent protocol shares minted with the first deposit | stress test |
| A6 | Low | Keeper tips claimable on dust leaves | No tip below 0.02 XNT claimed | — |
| A7 | Info | An emptied architect wallet (below rent) would make its tiny fee transfers fail and block play | Its cut goes to the reward pool in that case | — |

Accepted and documented at the time: rent of some bookkeeping accounts is never reclaimed (a few thousandths of XNT each: game wallet and Be-the-House share accounts); in Duels the opponent could see which elements the creator held (revisited and fixed in the third pass, H1); a block producer can influence its own slot hash (bounded, same as every on-chain RNG without VRF; further mitigated in the third pass, H3).

## Third internal pass on v2 (2026-10-07, later)

A third internal adversarial pass (again not independent) looked for ways to extract value through the games, the oracle inputs and the Artifact rules. Status of each finding:

| # | Severity | Finding | Status |
|---|---|---|---|
| H1 | High | **Duel element countering.** The element a player could play was tied to the Artifacts they held, which are public, so an opponent could see the creator's options and pick a counter. | **Fixed.** The element is decoupled from holdings: any of the four elements can be played, hidden by commit-reveal. A live Artifact of any tier is only the ticket to the arena, checked when creating and when joining. |
| H2 | High | **Expired draw as a free option + keeper ordering.** An expired lottery draw rolled its prize into the next round, so a participant could profit from letting an unfavourable draw expire; the keeper's ordering did not prioritize settling draws. | **Fixed.** An expired lottery draw now has no winner and its would-be prize (50% of the vault) goes to the burners' reward pool — never rolled over, never re-drawn; that round's chips and tickets are spent. The keeper settles rounds first, in the same pass as the draw. Session keys (bots) are barred from P2P games and Duels (`OwnerOnly`), so only the wallet owner can enter. |
| H3 | High | **Block-producer influence on slot hashes.** The producer of the target slot could in theory influence or withhold the hash that decides a house bet. | **Mitigated and disclosed.** No VRF exists on X1. Exposure stays capped (max net win per bet 0.25% of the free bankroll; all unsettled payouts ≤ 20% of the bankroll), and a new circuit breaker refuses house bets for the rest of the UTC day once the bankroll (net of LP deposits/withdrawals) has lost 10% since the day began. |
| H4 | High | **Oracle market-data manipulation.** A thin or exotic pool (or a single hour of trading) could set a chain's XEN price or liquidity. | **Fixed in the oracle.** Only pools quoted in an allowlisted liquid asset (wrapped native token, USDC/USDT/DAI, WETH) count, for price and for liquidity; the price pool is the eligible pool with the largest XEN-side liquidity (not volume); the burn price is the median of its hourly closes over the 24 h ending at the burn hour; each chain's prices are clamped to ±50% of the median of its reference price over the last 4 epochs (first epoch: ±50% of the aggregator token price); the XNT price is clamped to ±50% of the previous epoch's. |
| M1 | Medium | **Mission chips on the unvested amount.** Orbit / Moon Landing missions credited lottery chips on the full allocation, including the part later lost to an eject penalty. | **Fixed.** Chips are credited only on XNT actually paid out (as vested XNT is withdrawn, or at eject), never on the penalty. |
| L1 | Low | **Forge Drop overrun bound** was undocumented: luck can make winners' floors exceed the drop reserve. | **Documented.** The overrun comes from the free pool and is bounded: an epoch pays at most 10% of the free pool plus max(reserve, 15 XNT) in total; winners beyond reserve + max(reserve, 15 XNT) are refused. |
| L2 | Low | **Snapshot-only boosts.** A wallet could forge or borrow an Artifact just for the epoch snapshot and recycle or return it right after. | **Fixed.** A boost counts only for an Artifact held by the same owner at both the previous and the current epoch snapshot; only the best one per wallet counts. |

Also changed in this pass: `publish_epoch` now refuses `rate_cap = 0` (the oracle must always supply the boost-neutral cap, which the verifier recomputes); dynamic Artifact pricing was added (+5% per forge, ÷1.05 per quiet week, between base and 100× base) with a buyer-signed `max_price`.

## Moon Wars and Predictions (2026-10-07, before their mainnet upgrade)

Both games were added as real-XNT player-vs-player modes (`instructions/wars.rs`, `instructions/predictions.rs`) and reviewed the same way. What the review and the tests found:

| # | Severity | Finding | Status |
|---|---|---|---|
| G1 | High | **Compute budget.** Starting a match shuffles two decks with 18 Keccak hashes; the program used a software Keccak (the `sha3` crate), which exceeded the 200,000 compute units of a transaction, so no match could ever start. Found by the integration test. | **Fixed.** On-chain hashing now uses the runtime's Keccak syscall (same Keccak-256 output; the software crate is kept only for host-side unit tests). This also lowers the cost of every Merkle proof, bet and draw. |
| G2 | Medium | **Prediction rounds never closed.** Round accounts kept their rent and rounding dust forever. | **Fixed.** Each round counts claimed entries; `close_prediction_round` (permissionless, once every entry is claimed) sends the dust to the reward pool and the rent back to the first entrant. |
| G3 | Medium | **Stake stuck without price data.** If the XDEX pool had no swap after a lock or end time, the round could not resolve. | **Fixed.** After `PRED_MAX_DELAY` (24 h) without an observation, the round is refunded in full. Data that has left the 100-observation window also refunds; a late lock or settlement can therefore never pick a price. |
| G4 | Low | **Turn timer too short on localnet** (2 s) for multi-action turns. | **Fixed.** Explicit timers: 120 s on mainnet, 8 s in the localnet test build. |

Design checks: decks are shuffled with the hash of a block produced after both players joined and stored in the match account, so the draw order is identical for both and visible to both (no hidden information to exploit); every move is re-validated by the program (turn, mana, field limit, readiness, targets); the player to move loses on timeout and anyone can award it; a match ends in a draw with a full refund after 100 rounds. Predictions read the TWAP from the XDEX observation account only after checking its address, owner and pool; the computation was cross-checked against live mainnet data (15-minute TWAP $0.1989 vs spot $0.2004 at the time of the check). The pot cap (200 XNT) limits what a TWAP manipulation could win. Both games accept only the wallet owner (never a session key) and use the same 2% P2P rake.

Tests added: a scripted Moon Wars match played move by move against the program (illegal moves refused, winner paid exactly 98%), timeout and cancellation; a full Predictions round against a synthetic XDEX observation account (lock, settle UP, pro-rata payout, losing entry closed, one-sided round refunded, rounds closed); the randomized stress test now also plays Moon Wars with random legal and illegal moves and enters Prediction rounds, and the auditor checks the obligations of every match and round.

## Economics checked

- House games: RTP ≤ 98% for every parameter (exhaustive unit test). Bankroll keeps 0.5% of volume; at a 0.5% bankroll edge the Kelly-safe single-bet exposure is ≈0.5% → cap set at 0.25%.
- Rate cap K = 1.25 × liquidity-adjusted value (× tier multiplier, boosts excluded): beats the market route (40–90% of spot as of 2026-10-07, impractical below ~$11) while limiting mint-and-burn farming of an infinitely-mintable token. Boosts only shift shares within an epoch.

## Tests

- Rust unit tests: odds/RTP, duel cycle, Forge Drop odds (frequency and paid value match the expected value within 5% over 20,000 leaves).
- Program integration tests (local validator + Metaplex Core dumped from X1 mainnet): init, donations, publish limits and budget math, claims (instant/mission, permissionless, double-claim, wrong proof), vesting, eject, rate cap, epoch expiry, game wallet, exposure cap, coin flip settlement and roll recomputation, session keys, Be the House, Jackpot (multi-player and refund), Artifacts (forge split, chips, recycle), Duel, Burn Lottery, airdrop, Forge Drops (seal, always-win and random wins, keeper delivery, double-claim, XNT fallback guard, recycle of a dropped Artifact, cancellation), LP pricing and slippage, expired-draw handling (Jackpot refunds, lottery without a winner), epoch expiry with drops, solvency invariants.
- Randomized stress test (`tests/stress.test.ts`, reproducible with `STRESS_SEED`): 8 players and 3 LPs play house games with random parameters, Jackpots, Duels (reveals and timeouts), Moon Wars matches (random legal and illegal moves, timeouts), Prediction rounds, forge/recycle, LP deposits/withdrawals and wallet moves for many rounds; after every round an auditor reads **every account the program owns** and checks that each one holds what it owes, that `reward_reserved` and `bankroll_reserved` equal the sum of their parts, that LP shares add up and that pending payouts stay under 20% of the bankroll. Also: a whale betting at the exposure cap 40 times in a row, and a bank run where every LP exits while bets are pending (winners are still paid in full).
- Portal tests (Hardhat, mock reproducing XEN `burn()` semantics).
- Oracle tests: Merkle proofs, sybil-neutral scoring, boosts, dust, rate cap, data-hash determinism and tamper detection.
