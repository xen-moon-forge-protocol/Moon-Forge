The v3 oracle rules and the final program upgrade are decided but not live: everything below that is marked "planned" is dated and not yet true on-chain. Revised 2026-10-24: the planned oracle powers (the oracle seat, the 48-hour hold with bonded voids and the oracle key's operating allowance) and the proof-plan condition now follow the source of the final upgrade. ## Who can do what: status today and after the freeze

This block is the plain statement of what is immutable, what the bounded oracle still does, what the community can run without the project, and what depends on GitHub. The "after the freeze" column is the plan as decided on 2026-10-22, revised on 2026-10-24 where it named items the source of the final upgrade does not contain; the exact list of remaining powers is published with the final-upgrade announcement (at least 7 days before the upgrade) and finalised in the freeze record with both signatures.

| | Status today (2026-10-22, v2 live) | After the freeze (planned; earliest 2026-11-25) |
|---|---|---|
| **Immutable** | The five EVM portals (no owner, admin, fee, pause or upgrade). **Fixed under the live program** (no instruction can change them; only a program upgrade could, until the freeze): the airdrop root (set once on 2026-10-12) and every published epoch (its root and data hash are on-chain and its file is in git). | The program itself: no upgrade authority, IDL authority erased, so every constant, split, odd and vault rule is frozen. Plus everything in the left column. |
| **Who can change the program** | One upgrade authority (the architect wallet), held by the anonymous operator outside GitHub and never in its secrets; it moves to an offline signer from the final upgrade to the freeze. It is used only twice more: the announced final upgrade and the freeze. If that key were lost before the freeze, nobody could upgrade or burn the authority: the program would stay as deployed, with an authority nobody holds. | Nobody. |
| **What the oracle can do** | Publish one epoch per ≥ 6 days with a Merkle root it chooses, a data hash, a total score and a `rate_cap`; the program computes the budget as `min(10% of the free pool, total_score × rate_cap)` and refuses more. Hand its role to a new key (two-step). It cannot move vault funds, pay anyone outside a published leaf, or change a rule on-chain. The policy behind each root (prices, multipliers, boosts) is off-chain, versioned in this repository, and every epoch's inputs are published so anyone can recompute the root. | The same bounded publish power and hand-over, with these limits in the source of the final upgrade (as of 2026-10-24; true only once the upgrade transaction exists): every epoch is claimable only 48 hours after its publication, and during that hold anyone can void a wrong epoch with a bond paid to the pool; the oracle key sits in an oracle seat whose offline cold key can replace a stolen hot key; if the oracle goes silent (no epoch has survived its hold for 28 days), the largest voider can take the seat from day 28 and anyone from day 29, with a bond, and publish again with the same open code on the same pools. Nobody can veto either step, and the program has no pause instruction; from round 4 of that source (2026-10-25) a week without a paying burn does not count as silence, because the oracle then publishes an empty base epoch (nothing paid), and the hot key can never hand its role to the architect payee. That source also pays the publishing oracle key an operating allowance from the free pool at each publication: the new epoch account's rent back plus a top-up toward 0.25 XNT of at most 0.05 XNT, only from what the epoch's budget leaves of the 10% bound, never more than 1% of the free pool, and nothing while the oracle key is the architect payee; it is a running cost of the pool, never architect income. No oracle power ever gains control of vault funds. |
| **What the community can run** | `npm run verify` on every epoch file; the keeper (`npm run keeper`: claims, settlements, Forge Drop delivery, expiry — permissionless, tipped by the pool); the site, from any host (MIT); the oracle build in dry mode (`npm run epoch -- --dry`, which builds and prints the next epoch without publishing); a fork with its own program id and portals ([FORK.md](FORK.md)). It cannot publish an epoch (that needs the oracle key) or upgrade the program. | The same, plus the keeper for the games. No new chain will be added by this project; a portal elsewhere is a fork. The oracle code itself can be run by a community operator if the oracle key is handed over (two-step, on-chain) or, under the seat rules above, by whoever takes a dead seat. |
| **What depends on GitHub** | The site (Pages), the scheduled oracle, keeper and health runs (Actions) and the epoch-file feed (git + Pages). **If the account falls:** the site, the scheduled runs and the feed stop; new epochs pause until the oracle operator runs the same code elsewhere; already-published epochs stay claimable by anyone who holds the file (any clone) and an RPC; **the pool stays locked in the program** — nobody can take it, and it pays nothing until an epoch is published. No copy of the epoch files outside GitHub is planned: the copies are every clone of the repository and the oracle run's 90-day artifact, each checked against the data hash stored on-chain at publication. | Still GitHub-hosted, with the same consequences and the same copies of the epoch files. No routine action will ever be taken by the owner after the freeze; emergency off-chain fixes remain possible (one sealed credential kept offline with the key backups). A fork with a new oracle key cannot continue the same pool. |
| **Idle vaults** | Never staked, never lent. | Same, permanently: no staking path is added by the final upgrade. |
| **Owner actions left** | Fund the final upgrade once (2026-11); sign the final upgrade (earliest 2026-11-11); sign the freeze (earliest 2026-11-25, no later than 2026-12-31); the dated decision sheet. | None routine. |

## When the upgrade authority will be burned

Earliest **2026-11-25**, and only once all of these hold:

1. The final program upgrade is deployed as announced: `docs/UPGRADE-2026-11.md` (source commit, reproducible build procedure, changelog) published with the announcement at least 7 days before the upgrade, and the binary hash of the build commit published in the same file at least 48 hours before it.
2. The **mainnet proof plan** is complete, with a transaction link for every row: every front exercised once on mainnet by the project's own labelled test wallets with small amounts — burn on each of the five chains and each tier → epoch under the new binary → claim → vesting withdrawal and early exit; forge and recycle in each tier; every game once; Be the House deposit and withdrawal; the oracle seat's void, hot-key rotation and dead-seat take (where a mainnet step would delay real burners, proven on a local validator or a fork of mainnet accounts, with the run's log in place of the transaction link). **With or without external users:** the freeze does not wait for third-party burns.
3. **14 consecutive daily health runs with no FAIL** after the last proof-plan row — the measurable meaning of "stable": vault invariants, reconciliation of every epoch, oracle cadence, keeper backlog within its service levels, site current, verification green, privileged-change rows unchanged. The rows not yet in the health check, and a "stable-days streak" row, are added with the operations update, before the count starts; any fix to the program resets the count.
4. The Artifact metadata lives on Arweave and the collection points at it (`refresh_collection_uri`).

Then, in one session: `anchor idl erase-authority` and `solana program set-upgrade-authority … --final`. Before signing, the on-chain program bytes are compared with a reproducible build of the published source. Both transactions are announced on the project's channels and recorded in this file, SECURITY.md, the README and the site's Transparency page.

**No later than 2026-12-31.** If the final upgrade has not been deployed by then, the authority is burned on the then-current binary, with the games delisted from the site (disclosed), or a later fixed date is published with the same rule. The freeze cannot slip without a date.

After the freeze, nothing in the program can change; only the off-chain parts listed above (oracle policy inside the on-chain bounds, the frontend, the oracle key hand-over) can. No new EVM portal will be added.
